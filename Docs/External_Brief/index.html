01 — Overview

What was created

The TSS2 facility can now run instructor-authored training scenarios from JSON files without rewriting the scene, prefabs, equipment assets, endpoint labels, or the existing training-session singleton. The data is loaded from Assets/StreamingAssets/Scenarios, validated, then adapted into the existing TssScenarioDefinition shape that the simulator already understands.

External scenario package

A versioned manifest plus exactly four versioned JSON scenario files drive the four-choice Main Menu.

Runtime adapter

Validated external data becomes a transient scenario definition. Existing installation, cabling, binder, network, and evaluation code keeps its current contract.

Local authoring editor

A dependency-free browser tool imports, edits, checks, previews, saves a local draft, and downloads the JSON package.

Safe fallback

If a manifest or scenario fails validation, the original serialized scenario remains available instead of allowing a partial launch.

What JSON owns

  • Equipment/cable quantities, cabling, schedule and permanent connections.
  • Rack/station placement requirements, names, phases, network rules, evidence, and binder text.

What Unity still owns

  • Scene geometry, actual Unity assets, prefabs, endpoint bindings, simulation behavior, and evaluation engine.
  • Student-specific IP addresses, VLAN values, credentials, and other deterministic runtime values.
  • The final asset/facility validation decision before launch.

03 — Scenario Config Editor

How to use the web app

The editor is a local static page at sites/tss-scenario-config-editor/dist/index.html. It is intentionally not a hosted service and does not modify Unity assets or publish scenarios.

  1. Open the page through a local web server. Select Load shipped samples to load the current package, or choose Import manifest + scenarios and select manifest.json plus its referenced scenario files.
  2. Select a scenario. The drop-down chooses one of the imported entries. The JSON editor shows the full authored object for that scenario.
  3. Edit the authored data. Keep the format, schema version, scenario ID, display name, and scene aligned with the corresponding manifest entry. Edit only reference-free fields; never add Unity GUIDs, instance IDs, prefab references, transforms, or per-student credentials.
  4. Validate and preview. The browser checks the version-1 structure, required fields, duplicate identifiers, inventory quantities, rack ranges, and manifest identity. The Binder Preview shows authored sections without pretending to generate runtime tokens.
  5. Download and install. Download the scenario and, if changed, the manifest. Place the JSON files in Assets/StreamingAssets/Scenarios, preserving the filenames referenced by the manifest.
Important: browser validation is a quick authoring guardrail. Unity performs the final catalog, facility, asset, network-role, and launch validation.

04 — Unity workflow

Using edited JSON with TSS2

Package layout

Assets/StreamingAssets/Scenarios/
├── manifest.json
├── balanced-lab.json
├── installation-practice.json
├── network-verification.json
└── wireless-readiness.json

The manifest must be tss-scenario-manifest, schema version 1, and contain exactly four entries. Each entry's ID, name, scene, and filename must match its scenario file.

Run and test

  1. Back up instructor edits before using the sample-export command; it rewrites all four samples.
  2. Open MainMenu in Unity and enter Play Mode.
  3. Confirm four enabled scenario choices, then launch each choice with a last name and positive computer number.
  4. Use TSS → External Scenarios → Run Edit Mode Tests and Run Play Mode Tests.
  5. Review results in Temp/TssScenarioTests and resolve any [TSS Scenarios] warnings before release.

Authoring rules that matter

Stable IDs only

Use equipment IDs, cable IDs, rack IDs, station IDs, and endpoint IDs already known to the catalog.

Generated values stay out

Use binder tokens such as {ManagementVlan} and {Ssid}; do not hard-code generated addresses or passwords.

Current facility only

This schema configures the existing TSS facility, not arbitrary topologies or scene geometry.

05 — TSS2 support elements

What was added to the simulator

External DTO and schema identity

TssExternalScenarioData and manifest DTOs define a reference-free, versioned schema. Equipment and cable references use stable IDs rather than Unity object references.

Catalog and validator

TssScenarioCatalog maps allowed equipment/cables and snapshots supported facility IDs. The validator rejects invalid identities, duplicates, unknown assets, impossible quantities, invalid placements, VLAN/rack issues, and malformed supporting data.

Loader and adapter

TssExternalScenarioLoader loads local JSON through UnityWebRequest, validates it, and creates a temporary runtime TssScenarioDefinition. Authored ScriptableObject assets are never modified.

Startup and ownership safeguards

The menu displays valid external choices and disables duplicate clicks while loading. Runtime definitions pass through the existing launch handoff and are released when replaced or unloaded.

Network and cabling continuity

Student/scenario seeding still generates deterministic profiles. A bounded role/rack-range match resolves the CN-1 U30-to-U34 installation rule without changing endpoint IDs or physical scene data.

Tools, tests, and documentation

Editor commands rebuild the asset/facility catalog, export samples, and run focused tests. Documentation records the contract, limitations, recovery notes, and expected behaviors.

07 — Graphify local model setup

When Graphify needs a model

Graphify can build code structure locally with deterministic AST extraction. It does not use a vector database or embeddings model for its graph queries. A generative model is optional for semantic extraction of documents and richer inferred relationships, not a prerequisite for code-only indexing.

LM Studio recommendation

Run a chat/instruct or coding model capable of following structured prompts—not an embedding-only model. Use the exact model ID exposed by LM Studio's /v1/models endpoint.

$env:OPENAI_API_KEY = "lm-studio"
$env:OPENAI_BASE_URL = "http://localhost:1234/v1"
$env:OPENAI_MODEL = "<LM Studio model id>"

graphify extract "C:\path\to\repo" `
  --backend openai --max-concurrency 1 `
  --token-budget 4000 --api-timeout 900

Why these settings

  • LM Studio exposes an OpenAI-compatible local server, commonly at http://localhost:1234/v1.
  • OPENAI_API_KEY only needs a non-empty local value when the server does not require a real key.
  • One concurrent request is the safe starting point for a local model; increase only after observing stable throughput.
  • Graphify's installed package/skill version should be kept aligned before relying on a particular backend feature.

08 — Boundaries and next steps

What this work does not change

  • It does not change Unity scene geometry, prefabs, manual transforms, endpoint labels, or existing singleton authority.
  • It does not make the web editor a replacement for Unity validation, source control, or device-build testing.
  • It does not add FMS, aircraft, map, or approach fields to TSS scenarios.
  • It does not require an LM Studio model for normal Graphify structural indexing.

Use the editor to make focused JSON changes, let Unity validate and exercise those changes, and add a backend only when shared authoring, approvals, revision history, or remote delivery become real requirements.
