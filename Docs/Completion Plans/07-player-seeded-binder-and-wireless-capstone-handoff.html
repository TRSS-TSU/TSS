TSS2 · Completion Handoff

Player-Seeded Binder & Wireless Capstone

The seeded network profile, launch handoff, training Binder, and Balanced lab network data are implemented. WP4's physical equipment and interactive wireless workflow remain intentionally unimplemented until the required assets and scene attachment point are supplied.

Implemented

  • Student identity at launch.

    How it works: Enter a last name and a whole number greater than zero in the scenario menu. The menu trims extra spaces and normalizes letter case before constructing the student ID, so use the same name and computer number whenever the same student needs to repeat a lab.

  • Repeatable seeded profile.

    How it works: Select the same scenario with the same normalized student ID to regenerate the same network values. Change either value only when a new individualized profile is intended; restarting also creates a clean progress session, rather than retaining completed work.

  • Constrained network addressing.

    How it works: Read the assigned VLANs, LANs, and WAN circuit from the Binder before configuring devices. The generator deliberately keeps VLANs unique and valid and reserves VLAN 888 as the dead VLAN, so instructors do not need to hand-author values per student.

  • Wireless and circuit credentials.

    How it works: Use the Binder as the single student-facing source for the circuit ID, SSID, passphrase, AP password, channel, and AP management address. These values are generated once for the run and are also the values later checked by the evaluator.

  • Seven-tab Training Binder.

    How it works: Open the existing SOP panel and select the tab appropriate to the current work package. The Binder displays the active profile instead of duplicating settings in each device UI, so changes to a seeded value remain consistent across instructions and grading.

  • Authored Network Scenario lists.

    How it works: The Balanced scenario now contains serialized endpoint aliases, rack role bindings, required ports, and evidence requirements. Extend these lists by adding real scene endpoints and evaluator checks; do not overwrite endpoint aliases from role bindings, because aliases supply the endpoint-to-address mapping.

Empty Network Scenario lists

Resolved for the current Balanced scenario. The serialized scenario now supplies all four lists, and the runtime profile consumes them. The Required Ports list intentionally contains only the existing WP2 endpoint ports; adding AN-1 Fa0/7 before the AP exists would make WP2 impossible to complete.

The planned AP port (AN-1 Fa0/7 → AP-1) belongs in the WP4-specific evaluator when the AP workflow below is implemented.

Manual inputs still required

  1. Provide or approve AP and laptop models.

    How to complete: Supply the source models or approve placeholders, then make one placement prefab for each. Give the AP a visible Ethernet port and status LEDs; give the laptop a readable display and recognizable Wi-Fi state. Use a clean root transform, sensible colliders, and a named Ethernet-port child transform so cable attachment can target a stable object.

  2. Place Guest Lounge anchors.

    How to complete: Add empty scene transforms such as GuestLoungeApMount at the selected ceiling location and GuestLoungeLaptopTable on the selected table. Parent the AP and laptop placement points to these anchors, then verify their location from the player camera. Do not rename or move the existing ReceptionDesk, wallports, or configured endpoints.

  3. Author the Rack01 Port17 structured path.

    How to complete: Confirm the destination endpoint and whether the run should show a player-installed cable or retain an invisible permanent building cable. Add a permanent connection only after both endpoint transforms exist, route it from Rack01 patch-panel Port17 to the AP mount, and inspect the path in-scene for clipping or an ambiguous cable route.

  4. Add wireless equipment definitions and inventory.

    How to complete: Append new wireless categories rather than renumbering existing ones, create assets using the approved AP and laptop prefabs, and define their interfaces from the named anchors. Add exactly one of each to the Balanced scenario inventory, then confirm the existing equipment/session binder can resolve their endpoint IDs without changing existing items.

Play Mode acceptance check

  1. Compare two students.

    How to test: Launch Balanced_12_Piece_Lab twice with two distinct last-name/computer-number pairs. Open the Binder in each run and record the VLAN, LAN, circuit, and credential values; at least one generated profile value should differ.

  2. Repeat one student.

    How to test: Relaunch using the first student’s exact normalized identity. Confirm every Binder value matches the first run, then confirm equipment/session completion starts clean rather than inheriting the previous attempt.

  3. Protect WP1–WP3.

    How to test: Complete the existing work packages with the normal port, reachability, and evidence workflow. Treat a failure here as a regression: WP4 work must be isolated from the current required-port snapshot until its own evaluator is added.

  4. Check Binder coexistence and privacy.

    How to test: Open every tab with terminal and desktop sessions already visible, exercising tab switches and text readability. Inspect the Console afterward and confirm that passwords and other profile credentials were not emitted to logs.

  5. Exercise WP4 fault cases after asset delivery.

    How to test: Run one passing configuration, then change one fault at a time: uplink, VLAN, AP security, passphrase, lease, gateway/provider reachability, and RedWolf page result. Each fault should fail only its relevant requirement and report a player-understandable correction.

Rollback: revert the scoped seed, Binder, scenario-data, and test changes. No scene bindings, desk names, wallport IDs, or existing equipment categories were altered.
